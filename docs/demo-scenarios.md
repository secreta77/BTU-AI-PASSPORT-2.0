## სატესტო მონაცემები სცენარებისთვის
- სცენარი 4 (დავალების მაგალითი): BTU-AI-000125, Giorgi Kapanadze.
- სცენარი 1: Sheets-ში ახალი სტრიქონი ახალი Student ID-ით, Passport ID-ის გარეშე.
- სცენარი 6: სტრიქონი არარსებული Student ID-ით, მაგ. BTU-T-9999, **Passport ID შევსებული** (მაგ. BTU-AI-009999). თუ Passport ID ცარიელია, სისტემა სტრიქონს ახალ სტუდენტად აღიქვამს (სცენარი 1) და ნამდვილ პასპორტს გასცემს. მოსალოდნელი შედეგი: `Row N: unknown Student ID BTU-T-9999: its Passport ID BTU-AI-009999 is not in the database` (ცხრილში T სვეტი და ჟურნალი), Q = `NOT SYNCED`, სტუდენტი არ იქმნება. შეცდომიანი ხაზი ცხრილში რჩება და ყოველი sync-ის შეჯამებაში ითვლება, ამიტომ სცენარი 5 (`0 errors`) გადაიღეთ სცენარი 6-მდე.
- CONFIRMED-ის ფილტრი ჩართულია (სვეტი U "Verification Status"): `PENDING`/`REJECTED` რიგი პასპორტს არ ცვლის და sync-ის შემაჯამებელ ხაზში ითვლება `skipped`. სცენარები 3–4 ეხება `CONFIRMED` რიგებს.
- სცენარი 10: `server/scripts/tamper-pdf.js`, რომელიც ოფიციალურ PDF-ში სახელს ცვლის.

## სცენარი 10: გაყალბების დემო
1. `cd server && npm run tamper -- output/test.pdf` ქმნის `output/test-tampered.pdf`-ს (პირველ სახელს ცვლის, ვიზუალურად შეუმჩნევლად; ორიგინალი უცვლელია).
2. კონსოლში ჩანს ორივე SHA-256 და "ჰეშები განსხვავდება".
3. `/verify/<კოდი>` გვერდზე ავტვირთოთ `test-tampered.pdf`: შედეგი ❌ "ფაილი შეცვლილია". ორიგინალი `test.pdf` კი ✅ უნდა აჩვენოს.
4. დემოს აზრი: თვალი ვერ არჩევს, ბლოკჩეინი არჩევს.
